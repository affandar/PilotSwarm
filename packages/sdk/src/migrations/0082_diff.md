## Table Changes

### `webhook_retention_policy` -- new

```sql
CREATE TABLE IF NOT EXISTS SCHEMA.webhook_retention_policy (
    singleton BOOLEAN PRIMARY KEY DEFAULT TRUE CHECK (singleton),
    revision INTEGER NOT NULL DEFAULT 1,
    receipt_days INTEGER NOT NULL DEFAULT 30 CHECK (receipt_days BETWEEN 1 AND 3650),
    replay_days INTEGER NOT NULL DEFAULT 30 CHECK (replay_days BETWEEN 1 AND receipt_days),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_sweep_at TIMESTAMPTZ,
    next_sweep_at TIMESTAMPTZ
);
INSERT INTO SCHEMA.webhook_retention_policy(singleton) VALUES(TRUE)
    ON CONFLICT DO NOTHING;
```

The singleton coordinates cleanup across CMS instances. Policy changes require
the persisted administrator role and an exact revision. Cluster-scoped admins
can change deployment policy without gaining access to other owners' receipts.
Changes affect future terminal dispositions; already captured replay deadlines
cannot be extended by policy changes, duplicate deliveries or replay.

### `webhook_retention_totals` -- new

```sql
CREATE TABLE IF NOT EXISTS SCHEMA.webhook_retention_totals (
    owner_id BIGINT PRIMARY KEY,
    receipts_deleted BIGINT NOT NULL DEFAULT 0,
    payloads_deleted BIGINT NOT NULL DEFAULT 0
);
```

Durable aggregate counters contain no receipt IDs, credentials or payloads.
Reads preserve ordinary owner, cluster-admin and unrestricted/system scopes.

### `webhook_receipts` -- modified

```diff
+ settled_at TIMESTAMPTZ
+ receipt_expires_at TIMESTAMPTZ
+ replay_expires_at TIMESTAMPTZ
+ payload_expires_at TIMESTAMPTZ
```

Non-actionable terminal dispositions capture absolute deadlines. Queued
receipts and rows with outstanding outbox work never become age-based cleanup
candidates. The first replayable terminal failure captures a fixed replay
deadline; accepted replays clear cleanup eligibility until routing settles
again, without resetting that deadline. Consumption/drop makes the internal
payload immediately eligible for a bounded sweep, not the durable queue data.

Existing terminal rows are backfilled in bounded batches after migration,
receiving a full retention period from backfill rather than being purged all
at once based on their old timestamps.

## New Indexes

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS webhook_retention_due
    ON SCHEMA.webhook_receipts
    (COALESCE(LEAST(payload_expires_at,receipt_expires_at),'-infinity'::timestamptz),receipt_id)
    WHERE status IN (
        'consumed','dropped','unmatched','rejected','disabled','expired',
        'target_terminal','dead_lettered','routed','routing_failed'
    );
```

An unrecorded migration retry first drops this specific index concurrently,
avoiding a failed concurrent build's invalid-index residue. No blocking index
build or replacement of historical migrations is required.

## Function Changes

### Policy and bounded maintenance -- new

```diff
+ cms_webhook_retention_policy_json() RETURNS JSONB
+ cms_webhook_retention_update(JSONB, TEXT, TEXT, BOOLEAN) RETURNS JSONB
+ cms_webhook_retention_stamp() RETURNS TRIGGER
+ cms_webhook_outbox_retention() RETURNS TRIGGER
+ cms_webhook_retention_sweep(INTEGER) RETURNS JSONB
```

`webhook_retention_stamp` runs before insert/status updates on receipts;
`webhook_outbox_retention` runs after outbox deletion. The latter accounts for
existing finish/consumption functions whose status changes precede removal of
their routing work. Neither trigger changes session or orchestration state.

The sweep claims the policy row and eligible receipts using `FOR UPDATE SKIP
LOCKED`. It checks the absence of outbox work again under the receipt lock,
deletes expired internal payloads/history, and updates counters/schedule in the
same transaction. Replay still locks outbox before receipt; cleanup never locks
or deletes active outbox rows, and skips replay-owned receipt locks. Batch size
is 1-500. Full batches schedule another pass after one second; idle passes after
60 seconds. Crashes roll back both deletions and the schedule.

Delivery idempotency rows and `session_creation_keys` are never deleted. Once a
delivery has no receipts left, only its obsolete trace context is cleared.
Late duplicates retain their original acceptance/conflict behavior without
creating new receipts, queue items, capability uses or resurrected sessions.
