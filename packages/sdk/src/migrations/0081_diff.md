# Diff for migration 0081

Migration file: `migrations/webhooks-0081.ts` — `webhooksMigration`,
registered in `cms-migrations.ts`.

`webhook_payloads` has no public management read. It contains only the bounded
normalized provider projection, or a generic endpoint's bounded signal data;
never a raw provider body. Unmatched/rejected provider deliveries have no payload
row. The 65,536-byte JSONB-text storage ceiling accommodates PostgreSQL's JSON
spacing; ingress independently enforces the 32-KiB generic JSON byte limit.

The counter owner `0` is reserved for unattributed ingress refusals, visible
only in administrator aggregates. Creation keys deliberately **do not cascade
when a session is deleted**: a delayed retry must not resurrect it.

```diff
+ cms_webhook_principal(BIGINT) RETURNS JSONB

+ cms_webhook_user_active(BIGINT) RETURNS BOOLEAN

+ cms_webhook_mutate(TEXT, TEXT, TEXT, JSONB, TEXT, TEXT, BOOLEAN, BOOLEAN DEFAULT FALSE) RETURNS JSONB
+ cms_webhook_list(TEXT, TEXT, TEXT, BOOLEAN) RETURNS JSONB
+ cms_webhook_endpoint(TEXT, TEXT, JSONB, TEXT, TEXT, BOOLEAN, BOOLEAN DEFAULT FALSE) RETURNS JSONB
+ cms_webhook_endpoints(TEXT, TEXT, TEXT, BOOLEAN) RETURNS JSONB
```

Management functions require a registered, currently admitted principal and
owner/admin access. Connector provisioning/reference changes and template
approval/config changes require an administrator. Owner/source identity cannot
be patched. Updates use optimistic revisions. Reference-bearing fields are
masked before any management result is returned. Mutations write redacted
`authz_audit` records in the same transaction, including dedicated rotation and
quarantine actions.

Approval uses a distinct trusted `p_approve` flag plus the current persisted
admin/anonymous role. `p_admin` separately controls cross-owner access; cluster
administrators can approve their own resources without inspecting other owners.
Only receipt/metric reads enable the actor helper's `p_system_read` exception
for the canonical system principal; it never grants mutations.

Destination checks use current root ownership, role, visibility and explicit
write grants, not administrator break-glass access. An ownership change invalidates an existing target even if its
creator remains a writer. Templates must have the same owner and source as the
connector and a still-authorized approver. The trusted host additionally checks
current application-agent/namespace placement before every template route.

### Ingress and durable acceptance — new

```diff
+ cms_webhook_rate(TEXT, INTEGER) RETURNS BOOLEAN
+ cms_webhook_preflight(TEXT) RETURNS BOOLEAN
+ cms_webhook_ingress_config(TEXT, TEXT) RETURNS JSONB
+ cms_webhook_origin_rate(TEXT) RETURNS BOOLEAN
+ cms_webhook_ingress_failure(TEXT, TEXT) RETURNS VOID
+ cms_webhook_matches(JSONB, JSONB) RETURNS BOOLEAN
+ cms_webhook_transition(TEXT, TEXT, TEXT DEFAULT NULL) RETURNS VOID
+ cms_webhook_accept(TEXT, TEXT, INTEGER, TEXT, TEXT, JSONB, TEXT, JSONB DEFAULT '{}') RETURNS JSONB
```

Authentication reference reads are internal-only. Global/source/origin/binding
quotas use persisted atomic minute buckets. Origin quotas also count failed
authentication. Binding quotas reject the whole delivery before acceptance,
avoiding partial fan-out or burning a provider retry identity. Capacity is
bounded at 10,000 pending routes globally and 1,000 per origin.

Acceptance locks the origin and delivery identity, deduplicates the exact-body
digest, rechecks authority, and atomically persists receipt/payload/outbox rows
plus endpoint use accounting. At most 16 bindings can match. Repeated refused
source/terminal-target deliveries retain the original refusal rather than
becoming success-shaped duplicate acknowledgements.

Signed GitHub setup pings persist as unmatched metadata only; they cannot match
a binding or allocate routing work. Acceptance persists only a bounded
trace/span-ID link alongside the delivery. Trace context is internal and never
appears in the receipt/read APIs; it carries no bearer URL or payload.

### Leased routing and correlation — new

```diff
+ cms_webhook_claim(TEXT, INTEGER, INTEGER) RETURNS JSONB
+ cms_webhook_route_context(TEXT, TEXT) RETURNS JSONB
+ cms_webhook_finish(TEXT, TEXT, TEXT, TEXT, BOOLEAN) RETURNS BOOLEAN
+ cms_webhook_signal_disposition(TEXT, TEXT, TEXT, TEXT) RETURNS BOOLEAN
+ cms_webhook_signal_event_disposition() RETURNS TRIGGER
```

Claims require contract version 1, use `FOR UPDATE SKIP LOCKED` and a 60-second
lease, and count crashes toward the eight-attempt ceiling. Route context
reauthorizes source, owner, template revision/approval, binding revision, target
ownership and grants. Create-session identities are reserved durably as
UUID-shaped IDs derived from binding plus delivery identity; opt-in
repository/PR coalescing is serialized. Acknowledgements are lease-fenced and
cannot overwrite an already-consumed/dropped signal.
Coalescing replaces a terminal/deleted target for a new delivery but distinguishes
a hard-deletion tombstone from a reserved session still being created. The
previous session identity is never resurrected.

The signal disposition function atomically matches all of receipt ID, session
ID and signal ID plus a nonzero routing-attempt count, refusing foreign or
contradictory updates. It can recover a late consumption after a lost queue
acknowledgement/dead-letter and clears outstanding routing work. Claim,
acknowledgement, disposition and replay use the same outbox-before-receipt lock
order.

The new `webhook_signal_receipt_disposition` `AFTER INSERT` trigger on
`session_events` invokes the same correlator for trusted webhook-sourced
`session.signal_consumed` / `session.signal_dropped` metadata. It also correlates
`session.webhook_prompt_consumed` by receipt, target and the exact
`webhook:<receipt-id>` message ID after a routing attempt. Prompt consumption
means dispatch into an orchestration turn, not successful model execution.
The event and its
receipt update commit together, including for older workers which know the
signal envelope but not this store facade. An activity/process crash between
event persistence and a separate callback cannot lose the receipt disposition.

```sql
DROP TRIGGER IF EXISTS webhook_signal_receipt_disposition ON SCHEMA.session_events;
CREATE TRIGGER webhook_signal_receipt_disposition AFTER INSERT ON SCHEMA.session_events
    FOR EACH ROW WHEN (NEW.event_type IN (
        'session.signal_consumed','session.signal_dropped','session.webhook_prompt_consumed'))
    EXECUTE FUNCTION SCHEMA.cms_webhook_signal_event_disposition();
```

Receipt queries are owner/admin-scoped, capped at 100 and metadata-only; timelines
retain the latest 32 transitions. Replay requires literal confirmation, retained
routing data, renewed authorization and no active lease; at most three explicit
replays are permitted. Binding changes never silently retarget an old receipt.
Metrics have only finite provider/outcome labels.
Dry-run matching uses the connector's approved ADO project/build-definition
mapping and explicitly excludes GitHub setup pings.

The creation procedure is called **after** ordinary public SDK creation policy
and model/owner resolution. It serializes the reserved identity, uses the
existing CMS creation/owner procedures, rechecks provider eligibility, and
persists the creation config and named-agent metadata in one transaction.
Retries return the existing matching identity without overwriting title/config,
changing owner or resurrecting a deleted session.
