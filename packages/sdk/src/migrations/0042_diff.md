# 0042 — `user_role_from_signin`

Persists the last-observed authorization role for each user so the **worker**
can resolve `isAdmin` for a session owner.

## Why

The portal derives the role from the request JWT (Entra app roles, or the
`PORTAL_AUTHZ_*` email allowlist) and never stored it. A worker holds an
*owner*, not a token, and runs turns on the far side of a durable queue where
frequently **no request exists at all** — cron/`cron_at` firings, sub-agent
turns driven by a parent, crash recovery, orchestration replay. So there was
nothing for it to read, and `_resolveInspectViewer` returned `isAdmin: false`
unconditionally: agent inspect tools were user-scoped for everyone, admins
included.

Forwarding the JWT through the orchestration was rejected — it would persist a
bearer credential in replayed duroxide history, and it would freeze the role at
*request* time rather than *tool* time (the same defect that got
"stamp the role at session creation" rejected in the design).

## Schema

```sql
ALTER TABLE users ADD COLUMN IF NOT EXISTS role         TEXT;
ALTER TABLE users ADD COLUMN IF NOT EXISTS role_seen_at TIMESTAMPTZ;
```

Both nullable with no default, so every pre-existing row reads as "no role
observed" → no privilege. Nothing to backfill.

## New stored procedures

Both are `CREATE OR REPLACE` of **new** names — no existing return type
changes, so no `DROP FUNCTION` is required in this migration.

### `cms_set_user_role(provider, subject, email, display_name, role) → TEXT`

Upserts the user via `cms_register_user` (so email/display_name keep the
existing update-on-sighting freshness from 0030), then **replaces** `role` and
sets `role_seen_at = now()`. Returns the stored role.

Three deliberate choices:

| Choice | Reason |
| --- | --- |
| Role is **overwritten**, never `COALESCE`d | A demotion (admin → user) must land. 0030's COALESCE-merge rule for display fields would preserve the higher privilege forever. |
| Role is **not** a `cms_register_user` parameter | That function is called by sightings carrying no role — share grants, session creates. Folding role in would make every such call either wipe a good role or force merge semantics we must not have. |
| `role_seen_at` bumped on **every** write, not just on change | It records when the value was last *confirmed*, which is what a reader needs to fail closed on staleness. "When it last changed" is useless for that. |

Normalization: trimmed, lower-cased, and restricted to `admin` / `user` /
`anonymous`. Anything else becomes `NULL`. An unrecognized role must read as
"no privilege" rather than survive as opaque text a later caller might compare
loosely.

`anonymous` is a genuine value, not a placeholder: it is what an auth-disabled
deployment issues (`createNoAuthUnknownPrincipal`, principal `none:unknown`),
and the portal already treats it as full access
(`isAdmin = role === "admin" || role === "anonymous"`). Storing it lets the
worker reach the same conclusion instead of guessing.

### `cms_get_user_role(provider, subject) → TABLE(role, role_seen_at)`

Narrow read for the worker's viewer resolver. Returns **no row** for an unknown
principal; callers treat "no row" and "NULL role" identically, as no privilege.

Deliberately **not** folded into `cms_get_user_profile`: that would change an
existing function's return type (forcing a `DROP FUNCTION`, per the 0041
lesson) and would hand the role to every profile reader — including the
management-facing surface, where a privilege value has no business being.

## Callers

- `PgSessionCatalog.setUserRole` / `.getUserRole` (`cms.ts`)
- `PilotSwarmManagementClient.recordUserRole` / `.getUserRole` — **direct mode
  only**, deliberately not a Web API route. A remote caller able to write its
  own role would be a privilege-escalation primitive. Same posture as
  `recordAuthzAudit`.
- Portal `requireAuth` (`packages/app/web/server.js`) writes it after a
  successful authentication, throttled by an in-process TTL cache.
- `SessionManager._resolveInspectViewer` reads it, with a staleness ceiling
  that fails closed.
